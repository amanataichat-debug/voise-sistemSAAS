## 1. Что сделано в этой сессии (коммиты в `1410-kb-v2`)

### 1.1 Коммерческие предложения агента (было в `1310-kp-design`)

Агент присылал клиентам PDF, в котором **терялся текст**: пункты обрывались на
«• Ор», в разделе «Стоимость» пропадала сама цена. Причина — рендер на `fpdf2`:
при автопереносе страницы посреди ячейки `multi_cell` курсор уезжал.

- Новый рендер `backend/services/document_design.py` на **reportlab Platypus** —
  разбиение на страницы делает фреймворк, текст потеряться не может. Старый путь
  остался аварийным запасным (`_render_pdf_legacy`).
- Оформление: титульная обложка (крупный логотип, тип документа, «Для: клиент»,
  дата, контакты), шапка фирменного цвета, карточки преимуществ с галочками
  (пункт вида `**Заголовок** — пояснение`, от двух подряд), прайс-таблица,
  картинки из библиотеки агента (`image_file_ids`, до 4), блок «Следующий шаг» с
  контактами, колонтитул с номером страницы. Отступы автоматически поджимаются,
  если хвост в пару строк иначе уезжает на пустую страницу.
- Фирменный стиль у каждого агента свой: `agent_configs.brand_company_name /
  brand_color / brand_contacts / brand_logo_file_id`, UI — раздел «Документы» в
  настройках агента (`static/agent/branding.js`).
- В свойства PDF пишется `Creator = VoksiAI documents v2` — по нему сразу видно,
  каким кодом собран файл (у старого рендера поле пустое).

**Статус:** владелец проверил на живом агенте — работает.

### 1.2 База знаний v2 (главное в этой сессии)

Старая база — одно текстовое поле: правка одной цены = перезалив всей базы,
поиск только векторный, агенту всегда возвращались 3 куска (даже нерелевантных).

**Замер, от которого всё плясало.** По логу звонка владельца (`gpt-live-1`):
средняя задержка ответа **6,6 с**, максимум 9,2 с, при этом **поиска по базе в
том звонке не было вообще**. Один поход за функцией стоит ≈4 с (голосовая модель
идёт в делегирующий бэкенд `gpt-5.6-terra`: `[02:19.072]` передала запрос →
`[02:23.106]` вызов функции). Вывод: частые знания не должны требовать функции.

**Схема — три слоя, от бесплатного к дорогому:**

1. **Промпт (0 мс).** Пары «вопрос — ответ» и короткие секции вшиваются в system
   prompt (`agent_knowledge_service.build_prompt_block`, бюджет 8000 символов и
   60 пар). Агент отвечает сразу, функцию не вызывает.
2. **Postgres (9 мс на живой базе).** `search_entries` / `search_products` —
   ILIKE по заголовку, ключевым словам и тексту, ранжирование в Python. Цена
   каталога фильтруется в SQL: по числам («до 3000») вектора врут.
3. **Pinecone.** Только документы и только если первые два слоя молчат. Слабые
   совпадения (`score < 0.3`) отбрасываются — раньше агент сочинял ответ по
   нерелевантным кускам.

**Модель данных:** одна таблица `agent_knowledge_entries` на все виды знаний
(`qa` / `section` / `product` / `document`) + `agent_knowledge_gaps` (вопросы без
ответа, повторы складываются в одну строку). Документы векторизуются по
отдельности (`doc-<entry>-<i>`), правка одного файла не трогает остальные;
нарезка `smart_chunks` режет по заголовкам и абзацам, не разрывая прайс.

**Инструменты агента:** `search_knowledge_base` (слои выше) и `find_products`
(каталог → цена + `media_file_ids` для отправки фото клиенту).

**UI:** модалка с пятью разделами (`static/agent/knowledge-base.js`) —
Вопрос-ответ, О компании, Каталог, Документы, Чего не хватает. Плюс поле
«Проверить»: владелец вводит вопрос как клиент и видит, ответит агент мгновенно
или пойдёт в поиск.

**По деньгам:** звонок тарифицируется по минутам (5,47 сом/мин), поэтому знания в
промпте звонок **не удорожают**; задержки, наоборот, удорожают — в разобранном
звонке ~59 с из 179 с ушло в тишину ожидания (≈5,4 сома из 16,3).

### 1.3 Кэш статики

У владельца база знаний висела на «Загрузка…», вкладки не переключались. Код был
в порядке (воспроизвёл страницу локально в Chromium — всё работает): до браузера
доехал новый HTML и **старый JS**, потому что `StaticFiles` отдавал только ETag,
без `Cache-Control`.

`_CabinetStaticFiles` в `app.py`: html/js/css/json → `Cache-Control: no-cache`
(браузер сверяет ETag, получает 304); файлы с хешем в имени (бандл лендинга) →
год и `immutable`. Плюс база знаний больше не висит на «Загрузка…» — показывает
код ошибки и текст.

## 3. Анализ кабинета: где путаница и что предлагаю

Анализ сделан **по коду** (`backend/static/agent.html`, `agent/*.js`,
`js/sidebar.js`). Доступа к живому сайту и админке у сессии нет — контейнер не
пускает наружу, поэтому «посмотреть глазами прод» я не могу; всё ниже выведено
из разметки и логики.

### 3.1 Главная проблема: слово «Документы» означает три разные вещи

| Где | Что на самом деле |
|-----|-------------------|
| Карточка «Документы агента» в шторке | Инструкции агента: кто я, кому звоним, как говорим, что предлагаем |
| Раздел «Документы» в настройках агента | Фирменный стиль PDF (логотип, цвет, контакты) |
| Вкладка «Документы» в базе знаний | Файлы-источники знаний |

Владелец заходит в «Документы» и каждый раз попадает не туда. Это надо развести
по названиям:

- «Документы агента» (инструкции) → **«Инструкции агента»** или **«О компании и
  правила»**;
- «Документы» в настройках (брендинг) → **«Бланк документов»** или **«Фирменный
  стиль»**;
- «Документы» в базе знаний → **«Файлы-источники»**.

### 3.2 Вторая проблема: знания и файлы разнесены по двум карточкам

Сейчас в шторке агента две соседние карточки: «База знаний» и «Файлы агента».
При этом один и тот же файл нужен в обеих ролях: как источник ответов и как то,
что агент отправляет клиенту. Владелец уже на это жалуется — ощущение, что
«каталог, файлы и база стоят отдельно».

**Предложение: одна карточка «Знания и файлы»** с вкладками внутри:

1. **Вопрос — ответ** — мгновенные ответы (в промпте).
2. **О компании** — секции (цены, адрес, доставка).
3. **Каталог** — товары с ценой и фото.
4. **Файлы** — единый список библиотеки, у каждого файла два переключателя:
   «агент отправляет клиентам» и «агент ищет ответы внутри». Сейчас это два
   разных места и два разных действия.
5. **Чего не хватает** — вопросы без ответа.

Так у владельца один вход для всего, что знает и отправляет агент, и исчезает
вопрос «куда это класть».

### 3.3 Прочее, что заметно по коду

- Карточек в правой шторке семь, половина ведёт в модалки с похожими названиями.
  После объединения знаний и файлов станет шесть, и смысл каждой будет понятен.
- Пункт меню «Голосовые ассистенты» (`voice-assistants.html`) и агент обзвона
  живут отдельно, хотя голос у агента настраивается внутри агента. Для нового
  пользователя это два входа в одно и то же — стоит обсудить объединение.
- `knowledge-base.html` (отдельная страница базы знаний) закрыта редиректом, но
  пункт про неё остался в документации — чистить при случае.

## 4. Очередь работ (предлагаемый порядок)

### 4.1 Первым делом: задержка звонка 6,6 с → ~3 с

Это и есть то, что портит впечатление клиентов, и это прямые деньги (минуты).
Владелец уже согласовал, что делаем после базы знаний.

Что проверять (по логу звонка, который владелец пришлёт):
1. **Лишние функции.** У агента подключены 6 инструментов: календарь (3), Gmail
   (2), поиск. На каждом ответе модель перебирает, не нужна ли какая-то. На
   звонке Gmail и календарь нужны редко — замерить, сколько даёт отключение.
2. **Делегирующая модель** `gpt-5.6-terra` — те самые ≈4 с до вызова функции.
   Рассмотреть более быструю модель или обход делегирования для простых функций.
3. **Разрыв ответа.** В логе владельца `[01:26.486]` агент сказал «…может даже»,
   продолжение пришло в `[01:43.591]` — 17 секунд паузы внутри одной фразы.
   Отдельно разобрать по логам.
4. Подключение сессии 2,9 с в начале звонка — проверить, можно ли греть заранее.

**Нужно от владельца:** лог звонка, где агент реально искал в базе (чтобы
увидеть цену поиска в секундах после перехода на новую базу знаний).

### 4.2 Миграция старых баз знаний

У существующих агентов знания лежат в `agent_configs.kb_content` одним текстом.
Нужно: при открытии новой базы предложить «перенести старую базу» — разбить
текст по заголовкам на секции и создать записи. Без этого у старых агентов новая
вкладка пустая, хотя база у них есть.

## 5. Как проверять перед словом «готово»

1. **Локальная Postgres с SSL** (`/usr/lib/postgresql/16/bin`, сертификат
   самоподписанный — приложение требует SSL), `create_all`, запуск
   `python main.py` с `PRODUCTION=true`: стартовые `ensure_*` отрабатывают,
   страницы и API без 500.
2. **Сквозные тесты на настоящих строках БД** через `TestClient` с настоящим
   роутером (`backend/api/agent.py`), а не на заглушках.
3. **UI — в браузере**: Chromium лежит в `/opt/pw-browsers`, Playwright ставится
   через pip. Логин подделывается так: создать пользователя, выпустить токен
   `backend.core.security.create_jwt_token(user.id)`, положить в
   `localStorage.auth_token`, открыть `/static/agent.html`. Обязательно собирать
   ошибки консоли (`page.on("pageerror")`) — именно так нашлась причина «вечной
   загрузки».
4. **Честно разделять** проверенное локально и то, что покажет только прод
   (Pinecone, живые звонки, Evolution, Composio).

Зависимости, которых нет в контейнере по умолчанию и которые пришлось ставить:
`fastapi uvicorn sqlalchemy psycopg2-binary pydantic-settings httpx aiohttp boto3
openai pinecone msgpack websockets audioop-lts alembic pytz playwright reportlab
pypdf python-jose passlib bcrypt python-multipart email-validator`.
`pysher` и `pyaes` на Python 3.13 не собираются — ставить всё, кроме них.
