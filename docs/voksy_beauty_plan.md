# Voksy Beauty — архитектура и план (на согласование)

Ветка `2511-beauty` (от `2211-live-kyrgyz`), 25.11.2026. Документ отвечает на п. 21 ТЗ: что уже есть,
что переиспользуем, архитектура, база, API, ИИ, экраны, риски, этапы. Кода по ТЗ ещё нет — только план.

## 0. Коротко

- **Сделать можем.** Всё, что зависит только от нас (журнал записи, мастера, услуги, страница салона,
  кабинет клиента, ИИ-администратор, автоматизация, касса, зарплата, склад, лояльность, тарифы),
  делается на текущем стеке (FastAPI + PostgreSQL + наши страницы + PWA), без новых серверов.
- **Фундамент уже есть примерно на треть.** С 18–19.11.2026 в коде работают онлайн-запись (мастера,
  график, записи, ссылка `/b/<slug>`, виджет на сайт, QR, напоминания), сотрудники со своим входом и
  правами, финансы (выручка, расходы, прибыль, % и оклад мастера), каталог с фото и остатками, CRM,
  инбокс, аналитика, бот в WhatsApp/Instagram/Telegram с инструментами записи, голосовые функции
  записи, голосовой помощник владельца. Beauty строим **поверх этого**, а не рядом.
- **От нас не зависит** и требует договоров/доступов: онлайн-предоплата на счёт салона (MBANK,
  O!Bank, ELQR, Finik салона), фискальные ККМ, Apple/Google Wallet, официальный WhatsApp Business API.
  Это поздние этапы; до них оплаты вносятся в кассу вручную (наличные/карта/QR салона).
- **Объём большой** — это продукт уровня Altegio/YCLIENTS. Предлагаю 6 этапов; первый этап сам по
  себе продаётся салону (журнал + мастера + услуги + страница записи + ИИ-администратор + тарифы).

## 2. Архитектурные решения

### 2.1. Beauty — отрасль внутри платформы, а не отдельная система (рекомендую)

Один аккаунт, один вход, одна база, один бот. «Voksy Beauty» = отраслевой режим кабинета: свои
тарифы, свой лендинг-вход, свой набор меню и экранов для салона. Включается нишей бизнеса (группа
`booking`: салон, барбершоп, маникюр, СПА, косметология — уже есть в `niche_catalog`) или выбором
Beauty-тарифа. Плюсы: ИИ-агент, голос, инбокс, CRM, кошелёк, оплата, аналитика работают сразу;
действующие клиенты не задеты. Минус: старые страницы записи придётся аккуратно расширять, а не
писать с нуля. Отдельная система (свой домен, свои таблицы клиентов) — это дублирование агента,
CRM и инбокса и разъезд данных; не рекомендую.

### 2.2. Организация и филиалы

- **Организация = аккаунт владельца (`users`).** Все таблицы уже изолированы по `user_id`; так и
  оставляем, новых «tenant»-слоёв не вводим.
- **Филиал** — новая таблица `beauty_branches`. `branch_id` получают мастера/ресурсы, записи, касса,
  склад. У существующих данных `branch_id = NULL` = «основной филиал» → миграция без поломки.
- Сотрудник видит только филиалы из своего списка (проверка на сервере в каждом запросе).

### 2.3. Роли и права — расширяем `team_members`

- Владелец = `users`; суперадмин = `users.is_admin`; сотрудники = `team_members`; клиент = новая
  таблица `client_accounts` (вход по телефону, см. 2.7).
- В `team_members`: `role` (manager / admin / master / accountant / custom), `branch_ids`,
  `resource_id` (мастер ↔ своя колонка календаря), тонкие права ключами: `schedule.view_all`,
  `schedule.edit`, `clients.view`, `clients.phones`, `clients.export`, `finance.view`,
  `finance.edit`, `payroll.own`, `payroll.all`, `inventory`, `loyalty`, `settings`, `staff.manage`.
- Роль = готовый набор прав, владелец может поправить любую галочку.
- Мастер по умолчанию: свои записи, свой заработок, свои клиенты без телефона (если владелец не дал
  `clients.phones`). Фильтр «только свои» — в сервисе, а не в интерфейсе.
- Проверка как сейчас: middleware по маршруту + проверка строки в сервисе (мастер не откроет чужую
  запись по id).

### 2.4. Услуги — остаются в каталоге агента

Услуга = позиция `agent_knowledge_entries` (как сейчас). Поэтому бот, голос, поиск, прайс в промпте
звонка и карточки с фото получают актуальные услуги **сами**, без синхронизации. Бьюти-поля — в
отдельных таблицах рядом (`beauty_service_settings`, `beauty_service_masters`), каталог магазинов и
других ниш не меняется.

### 2.5. Журнал записи и защита от двойной записи

- Визит (`visit_id`) = одна или несколько услуг подряд, у каждой своя запись `bookings` с мастером.
- Каждая запись занимает 1..N ресурсов (мастер + кабинет/кресло/аппарат) → таблица
  `booking_allocations` (запись, ресурс, начало, конец).
- **Защита в базе:** ограничение `EXCLUDE USING gist (resource_id WITH =, tstzrange(start_at, end_at) WITH &&)`
  для активных статусов (расширение `btree_gist`, проверить на Render). Даже если бот, админ и
  клиент по ссылке нажмут в одну секунду, пройдёт одна запись, остальные получат «время занято» и
  новые окна. Текущая блокировка строки мастера остаётся первым рубежом (она учитывает буфер).
- Статусы: `booked` (новая) → `confirmed` → `arrived` → `in_progress` → `completed`; `cancelled`,
  `no_show`. Выручка считается по `arrived/in_progress/completed` (сейчас — по `arrived`; совместимо).

### 2.6. Мгновенная синхронизация

Redis у нас нет, воркеров 4. Делаем на PostgreSQL: после изменения записи — `pg_notify('beauty', …)`,
в каждом воркере один поток слушает (`LISTEN`) и раздаёт событие открытым страницам по SSE
(`EventSource`). Если соединение оборвалось — страница перезапрашивает день. Опрос раз в 60 с
остаётся запасным.

### 2.7. Кабинет клиента без SMS

SMS у нас не работают. Вход клиента:
1. **Ссылка в подтверждении записи** (WhatsApp/Telegram) — подписанная, открывает «Мои записи» без пароля.
2. **Код в WhatsApp/Telegram салона** для входа с публичной страницы.
Один клиент может ходить в несколько салонов: аккаунт клиента — по номеру телефона, связан с
карточками `agent_contacts` разных организаций; салон видит только свою карточку.

### 2.8. Тарифы — из кода в базу

Сейчас цены в `SUBSCRIPTION_PLANS_CONFIG`, и `ensure_plan_prices()` при каждом старте перезаписывает
базу. Для Beauty: `subscription_plans` получает `product` (`voksy` | `beauty`), `limits` (JSON:
мастера, филиалы, ИИ-кредиты в месяц, голосовые минуты, модули), `trial_days`, `is_public`,
`for_user_id` (индивидуальный). Редактор у суперадмина. Старт-синхронизация больше не трогает
тарифы, отредактированные в админке. Доступ к модулю = проверка лимита/модуля тарифа на сервере
(одна функция), а не `if plan == …` в коде.

### 2.9. ИИ работает через серверные инструменты

Агент не придумывает цены и время: всё — ответ инструмента из базы. Создание, перенос и отмена —
**в два шага**: инструмент сначала возвращает итог («маникюр, Айгуль, завтра 18:00, 1 200 сом») и
`confirmation_id`; выполнить можно, только если после итога клиент ответил согласием (проверка в
коде, как уже сделано у голосового помощника владельца — `owner_confirmation`). Время повторно
проверяется в момент записи.

## 4. API

Новые префиксы (обработчики без `await` — `def`, как принято в кабинете):

- `/api/beauty/branches` — филиалы.
- `/api/booking/*` — расширяем существующий: месяц, перенос перетаскиванием (`PATCH` с проверкой),
  блоки времени, отпуска, повторяющиеся, лист ожидания, визит из нескольких услуг, кабинеты; `GET /api/booking/stream` — SSE.
- `/api/beauty/staff` — карточка мастера, портфолио, свои цены, приглашение в кабинет.

долги) · Финансы и отчёты · Зарплата · Склад · Лояльность · Автоматизация · ИИ-администратор
(существующая страница бота) · Инбокс (есть) · Отзывы · Тариф и оплата · Журнал действий.

**Мастер (телефон в первую очередь)**: моё расписание · запись · отметить «пришёл/завершил» · мой
заработок · уведомления.

**Бухгалтер**: финансы, касса, зарплаты, склад (отчёты).

**Клиент**: страница салона · запись по шагам · подтверждение · мои записи (перенос, отмена,
повтор) · история · отзывы · бонусы, сертификаты, абонементы · любимые мастера.

**Суперадмин**: тарифы и лимиты, промокоды, допуслуги, индивидуальные тарифы, салоны (есть
«Клиенты»).

### Сквозные сценарии (по ним пишем тесты)

1. Клиент в WhatsApp: «хочу на маникюр завтра вечером» → услуги и окна из базы → итог → «да» →
   запись → подтверждение с адресом и ссылкой «Мои записи» → у администратора и мастера сразу в
   журнале → мастеру уведомление → напоминания за сутки и 2 часа → после визита запрос отзыва →
   через N недель приглашение на повтор.
2. Запись по ссылке из Instagram: филиал → услуга → любой мастер → время → телефон → подтверждение.
3. Звонок: голосовой агент записывает в тот же журнал.
4. Бот и администратор в одну секунду берут одно окно → проходит одна запись, вторая получает
   «занято» и новые окна.
5. Визит: «пришёл» → «выполняется» → «завершена» → оплата картой + бонусы → списание материалов по
   техкарте → % мастеру → бонусы клиенту.
6. Отмена → окно освободилось → первому из листа ожидания приходит предложение.
7. Владелец голосом: «сколько заработали сегодня и кто лучший мастер?» → цифры и карточки.
8. Мастер с телефона видит только свои записи и свой заработок; чужую запись по ссылке открыть не может.

   чужих мастер не может; телефоны клиентов — только если владелец включил «Мастера видят телефоны».

3. ✅ **Услуги** (25.11.2026). Экран «Услуги» в журнале записи: прайс по категориям и подкатегориям
   (хранятся в коллекции каталога как «Волосы / Окрашивание», порядок и переименование — окно

   стороны. Услуги остаются позициями каталога бота — бот, звонок, поиск и прайс в промпте видят
   новые поля сами (цена диапазоном, предоплата, «записывает администратор»). Кабинет/кресло как

   по ссылке) за полсекунды приходит всем открытым журналам и кабинетам мастеров
