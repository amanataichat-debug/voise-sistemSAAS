# Памятка: SIP-шлюз Voksy AI на VPS

Простыми словами: что это за сервер, как к нему подключиться и что на нём делать.

## Что это за сервер

| Параметр | Значение |
|---|---|
| Роль | Приём и отправка телефонных звонков через SIP-транк оператора O! (ООО «НУР Телеком») |
| Хостинг | Hetzner Cloud, сервер CX23, дата-центр Falkenstein (Германия) |
| Публичный IP | `178.105.79.237` (статический, именно он указан в анкете оператора) |
| ОС | Ubuntu 24.04 |
| Имя хоста | `voksyai` (в приглашении терминала видно `root@voksyai:~#`) |
| Что установлено | Asterisk 20 (SIP-сервер) + мост `voksy-bridge` (Python, наш код) |
| Кто ставил | Скрипт `install.sh` из этой папки, одной командой |

Зачем он нужен: Render не даёт статический IP и не пропускает UDP, а оператору
для SIP нужны и то, и другое. Поэтому телефонная часть живёт на этом VPS, а
«мозги» (OpenAI/Gemini, диалоги, CRM) остаются на Render. Мост на VPS сам
подключается к Render по WebSocket, входящих соединений с Render на VPS нет.

Схема звонка:

```
Телефон абонента → сеть O! → 195.216.237.6/.7 → [VPS 178.105.79.237]
    Asterisk (SIP 5060/UDP, RTP 10000-20000/UDP)
        └─ AudioSocket (localhost:9092) ─→ bridge.py
                └─ WebSocket wss://voksyai.online/ws/sip/{call_id} ─→ Render
                        └─ handler OpenAI / Gemini → ответ голосом обратно тем же путём
```

## Как подключиться с компьютера

Подключение идёт по SSH из PowerShell на Windows. Ключ уже создан и лежит в
`C:\Users\<вы>\.ssh\id_ed25519`, публичная часть добавлена на сервер при его
создании в Hetzner.

1. Открыть PowerShell (Пуск → набрать `powershell` → Enter).
2. Выполнить:
   ```powershell
   ssh root@178.105.79.237
   ```
3. Приглашение сменится на `root@voksyai:~#`. Всё, вы на сервере.
4. Выйти обратно на компьютер: команда `exit`.

Как понять, где вы находитесь:

| Приглашение | Где вы | Что здесь выполнять |
|---|---|---|
| `PS C:\Users\...>` | На своём компьютере | `ssh`, `scp`, `ssh-keygen` |
| `root@voksyai:~#` | На сервере | `systemctl`, `journalctl`, `asterisk`, `curl`, `cat` и всё остальное из этой памятки |

Частая ошибка: набрать `ssh ...` или `scp ...`, уже находясь на сервере.
Эти команды всегда запускаются на компьютере.

Если после пересоздания сервера в Hetzner SSH пишет `REMOTE HOST IDENTIFICATION
HAS CHANGED`, выполнить на компьютере:
```powershell
ssh-keygen -R 178.105.79.237
```
и подключиться заново.

Передать файл с компьютера на сервер (тоже на компьютере):
```powershell
scp C:\путь\к\файлу root@178.105.79.237:/root/
```

## Что где лежит на сервере

| Путь | Что там |
|---|---|
| `/etc/asterisk/pjsip.conf` | Транк оператора `o-trunk` (оба их сервера, авторизация по IP), тестовый софтфон `test` |
| `/etc/asterisk/extensions.conf` | Маршрутизация звонков в мост |
| `/etc/asterisk/rtp.conf`, `manager.conf`, `modules.conf` | Порты RTP, доступ моста к Asterisk (AMI), отключённые модули |
| `/etc/asterisk.orig/` | Копия исходных конфигов Asterisk, сделана один раз при первой установке |
| `/opt/voksy-bridge/bridge.py` | Код моста (копия `infra/sip-gateway/bridge/bridge.py` из репозитория) |
| `/opt/voksy-bridge/venv/` | Python-окружение моста |
| `/etc/voksy-bridge/bridge.env` | **Секреты**: `GATEWAY_TOKEN`, пароль AMI, пароль тестового софтфона, адрес бэкенда. Никому не пересылать |
| `/etc/systemd/system/voksy-bridge.service` | Служба моста (автозапуск, перезапуск при падении) |

Конфиги на сервере **не редактируются руками**. Правильный путь: изменить файл в
репозитории в `infra/sip-gateway/`, закоммитить в ветку, затем на сервере
запустить обновление (см. ниже). Скрипт перезапишет конфиги и код моста, а
`bridge.env` с секретами оставит как есть.

## Повседневные команды (на сервере)

Состояние служб:
```bash
systemctl status asterisk voksy-bridge
```

Лог моста в реальном времени (Ctrl+C, чтобы выйти):
```bash
journalctl -u voksy-bridge -f
```
Здесь видно каждый звонок: `inbound … registered`, `answered`, `clear`,
`ended: reason (in=… out=… dur=…)`. `in` и `out` — число кадров звука по 20 мс
в каждую сторону. Если `out=0`, ассистент ничего не сказал.

Последние 200 строк лога:
```bash
journalctl -u voksy-bridge -n 200 --no-pager
```

Здоровье моста (подключён ли к Render и к Asterisk):
```bash
curl -s http://127.0.0.1:9091/health
```
Ожидается `"control_connected": true` и `"ami_connected": true`.

Перезапуск:
```bash
systemctl restart voksy-bridge      # только мост, звонки не трогает Asterisk
systemctl restart asterisk          # Asterisk, обрывает активные звонки
```

Консоль Asterisk (выход: `exit`):
```bash
asterisk -rvvv
  pjsip show endpoints      # o-trunk и test должны быть в списке
  pjsip show identifies     # IP оператора → o-trunk
  core show channels        # активные звонки
  pjsip set logger on       # показать SIP-пакеты (для разбора проблем с оператором)
```

Посмотреть секреты (например, пароль софтфона или токен):
```bash
cat /etc/voksy-bridge/bridge.env
```

## Обновление шлюза после правок в репозитории

На сервере одной командой (ветка `1409-sip-v1`):
```bash
curl -fsSL https://raw.githubusercontent.com/amanataichat-debug/voise-sistemSAAS/1409-sip-v1/infra/sip-gateway/install.sh | bash
```

Скрипт идемпотентный: перекачивает конфиги Asterisk и `bridge.py`, ставит
зависимости, перезапускает службы, в конце печатает сводку с проверками
`[ok]`. Секреты не меняются. Другую ветку можно указать так:
`VOKSY_BRANCH=main curl … | bash`.

## Связка с Render

На Render в переменных окружения сервиса должен стоять `SIP_GATEWAY_TOKEN`,
равный `GATEWAY_TOKEN` из `/etc/voksy-bridge/bridge.env`. Если они не
совпадают, мост в логе пишет `403` при подключении к control-сокету.

Во время деплоя на Render мост на 1–2 минуты теряет соединение и пишет
`backend_unavailable` или переподключается с backoff. Это нормально, звонки в
этот момент не обслуживаются.

## Тест без оператора (софтфон)

Транк у оператора уже включён, так что это запасной путь: он проверяет
Asterisk, мост и Render, не трогая оператора.

| Поле в Zoiper / MicroSIP | Значение |
|---|---|
| Сервер / домен | `178.105.79.237:5080` (транспорт UDP) |
| Пользователь | `test` |
| Пароль | `TEST_SIP_PASSWORD` из `bridge.env` |

- Набрать `100` — эхо-тест Asterisk, проверяет SIP и звук без Render.
- Набрать `996705701707` — звонок пойдёт как входящий на этот номер, ответит
  ассистент, который привязан к номеру в `/api/sip/numbers`.

## Номер и формат набора

| Параметр | Значение |
|---|---|
| Номер по карточке | `+996705701707` / `0705701707` |
| Каналов | 5 входящих + 5 исходящих |
| SIP оператора | `195.216.237.6:5070`, `195.216.237.7:5070` (работают оба) |
| RTP оператора | `195.216.237.6`–`.9`, порты 10000–65535 |
| Авторизация | по IP, без логина и пароля |

Внутри Voksy номера канонические — `996705701707`. Оператор же требует в INVITE
**national**-формат (`070`/`050`) и для А-номера, и для Б-номера. Мост
конвертирует их сам (`to_national()` в `bridge.py`), поэтому в API и в журнале
звонков везде пишем канонический формат — руками ничего переводить не надо.

Завести номер в системе (нужен JWT администратора):

```bash
curl -X POST https://voksyai.online/api/sip/numbers \
  -H "Authorization: Bearer <JWT>" -H "Content-Type: application/json" \
  -d '{"phone_number":"996705701707","label":"O! основной",
       "assistant_type":"openai","assistant_id":"<uuid ассистента>"}'
```

## Если оператор отвечает `403 Forbidden`

Так оператор реагирует на любое несовпадение данных INVITE с карточкой. Порядок
разбора — тот же, что в инструкции оператора:

1. Включить SIP-лог и повторить звонок:
   ```bash
   asterisk -rvvv
     pjsip set logger on
   ```
   Либо снять пакеты целиком: `tcpdump -i any -n -s0 -w /tmp/sip.pcap udp port 5060 or udp port 5070`
   (файл забрать через `scp` и открыть в Wireshark).
2. Найти в логе исходящий `INVITE` и сверить четыре поля с карточкой:

| Поле INVITE | Должно быть | Частая ошибка |
|---|---|---|
| `Request-URI` | `sip:0555123456@195.216.237.6:5070` | Б-номер в формате `996…` или `+996…` |
| `From` | `<sip:0705701707@178.105.79.237>` | А-номер не наш или не в national |
| `To` | `sip:0555123456@195.216.237.6` | — |
| `Contact` | `<sip:asterisk@178.105.79.237:5060>` | не наш IP (NAT, сменился IP сервера) |

3. Если номера в INVITE оказались в формате `996…` — сломалась конвертация в
   мосте. Проверить `COUNTRY_CODE`, `NATIONAL_PREFIX`, `SUBSCRIBER_DIGITS` в
   `/etc/voksy-bridge/bridge.env` и строку `originating to … (dial …)` в
   `journalctl -u voksy-bridge`: в ней видно оба формата сразу.
4. Если все поля совпадают, а `403` остаётся — вопрос к оператору: наш IP или
   номер не заведены у них в базе.

## Файрвол в Hetzner Cloud

Файрвол настроен в панели Hetzner (Cloud Console → проект → Firewalls) и
привязан к серверу:

| Порт | Протокол | Зачем |
|---|---|---|
| 22 | TCP | SSH |
| 5060 | UDP | SIP от оператора |
| 5080 | UDP | Тестовый софтфон (**удалить после запуска с оператором**) |
| 10000–20000 | UDP | RTP (звук) |

Исходящие соединения не ограничены. Порты 9091, 9092 и 5038 слушают только
localhost и снаружи недоступны.

## Типичные проблемы

| Симптом | Причина | Что делать |
|---|---|---|
| В логе моста `403` при подключении | Токен на Render не совпадает с `bridge.env` | Сверить `SIP_GATEWAY_TOKEN` на Render с `GATEWAY_TOKEN` |
| `backend_unavailable`, `bad_start` | Идёт деплой на Render | Подождать 2 минуты |
| Оператор отвечает `403 Forbidden` на INVITE | Номер в INVITE не в формате `070`/`050`, либо IP не совпадает с карточкой | См. раздел «Если оператор отвечает `403 Forbidden`» |
| Звонок есть, звука нет | Закрыт UDP 10000–20000 в файрволе или у оператора другой RTP-диапазон | Проверить файрвол, `pjsip set logger on`, смотреть SDP |
| Звук только в одну сторону | RTP оператора приходит с другого IP (`.8`/`.9`), чем указан в SDP, и его режет `strictrtp` | Временно `strictrtp=no` в `rtp.conf`, повторить звонок; если помогло — сообщить оператору |
| Исходящий падает с `channel_limit` | Заняты все 5 каналов оператора | `curl -s 127.0.0.1:9091/health` → `active_outbound`/`active_inbound` |
| Входящий слышит «занято» сразу | Заняты все 5 входящих каналов, мост отказал | В логе моста `inbound call rejected: all 5 channels busy` |
| Ассистент молчит (`out=0`) | Проблема на стороне Render: смотреть логи Render по `SIP-MEDIA` и `call_id` | Логи Render → строки `reply latency`, `finished` |
| Софтфон не регистрируется | Порт 5080 закрыт или неверный пароль | `cat /etc/voksy-bridge/bridge.env`, проверить файрвол |
| SSH: `HOST IDENTIFICATION HAS CHANGED` | Сервер пересоздан | На компьютере `ssh-keygen -R 178.105.79.237` |

## Если сервер придётся пересоздать

Rebuild в Hetzner стирает диск полностью. Порядок восстановления:

1. Ubuntu 24.04, тот же SSH-ключ, привязать тот же файрвол.
2. На компьютере `ssh-keygen -R 178.105.79.237`, подключиться.
3. Запустить `install.sh` (команда выше).
4. Из итоговой сводки взять новый `GATEWAY_TOKEN`, прописать на Render как
   `SIP_GATEWAY_TOKEN`, сделать redeploy.
5. Проверить `curl -s http://127.0.0.1:9091/health`.

IP при rebuild сохраняется. Если сервер удалить и создать заново, IP изменится,
и оператору придётся сообщать новый.

## После запуска у оператора

- Убрать правило 5080/UDP из файрвола Hetzner.
- Удалить секции `test` из `infra/sip-gateway/asterisk/pjsip.conf` и транспорт
  5080, закоммитить, запустить обновление на сервере.
